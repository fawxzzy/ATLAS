## Automation-Candidate Admission Threshold

A repeated workflow is only an honest automation candidate when all of the following are explicit and stable:

1. the repeated action family is named and has recurred with the same operator intent
2. the trigger surface is explicit
3. the required inputs are stable enough to enumerate
4. the proof or success artifact is explicit
5. the failure boundary is explicit
6. the safe fallback path is explicit
7. the owner and approval boundary are explicit
8. the critical path does not depend on hidden toggles, ad hoc prompting, or an unresolved external/session defect

If a repeated workflow fails any of the eight checks above, it may still be structured repetition, but it is not yet an honest automation candidate.

## Bounded Automation Candidate Ladder

The reusable ladder is:

1. manual repetition
2. structured repetition
3. automation candidate
4. automation-ready

Threshold meaning:

- `manual repetition`: repeated work exists, but the trigger or outcome is still fuzzy
- `structured repetition`: the family is recognizable, but one or more candidate-admission checks are still missing
- `automation candidate`: trigger, inputs, proof, boundary, and fallback are explicit and stable enough to target bounded helper work
- `automation-ready`: a real governed operator surface exists with verification, rollback or safe-fail posture, and repeatable proof

This pass freezes the ladder, but it does not move any family into `automation-ready`.

## Exact Non-Claim Boundaries

Do not claim automation readiness because:

- the same operator task happened multiple times
- a prompt can be copied forward
- the proof doctrine got clearer
- a packet can be drafted automatically even when the proof hop is still manual or blocked
- a blocked live bridge path has a strong restart receipt

Also do not collapse these distinctions:

- proof-packet preparation is not the same thing as proof capture
- automation candidate is not the same thing as automation-ready
- repeated prompting is not the same thing as a stable trigger surface
- external/session-scoped blockage is not the same thing as owner-repo automation debt

## Rule

`Automation Follows Stable Repetition`

Do not promote a repeated workflow into automation candidacy until its trigger, inputs, proof artifact, and fallback path are all explicit and stable.

## Pattern

`Operator Repetition Ledger`

Repeated operator actions should be captured as named families with trigger, boundary, and proof expectations so automation work targets real repetition instead of vague friction.

## Failure Mode

`Automation Claim Inflation`

If a workflow still depends on hidden toggles, ad hoc prompting, or unstable proof capture, calling it automation-ready creates false confidence and downstream churn.
