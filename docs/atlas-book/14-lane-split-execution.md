# Lane Split Execution

## Purpose

This chapter turns the future Fitness / Discord / ATLAS split into a practical reopen checklist.

It is the execution companion to:

- the lane split readiness plan
- the system map
- the restart guide
- the vision/endgame review

## Three Lane Reopen Model

The stack should reopen through:

1. Fitness app lane
2. Discord work lane
3. ATLAS systems lane

Each lane needs:

- valid start conditions
- required first checks
- required receipts
- explicit blocker awareness
- a first safe package

## Fitness App Lane

### Start conditions

- work belongs to Fitness product/runtime truth
- work belongs in `repos/fawxzzy-fitness`
- no DiscordOS extraction work is being disguised as normal product work

### Required first checks

1. confirm owner surface is Fitness
2. confirm whether the task is ordinary product work or approval-gated data hygiene
3. confirm deploy authority is still `_stack`
4. confirm the latest Fitness receipt chain

### Required receipts

- repo-local proof and release receipts
- Fitness Supabase approval receipts if touching approved hygiene work

### Approval-gated blockers

- Fitness Supabase mutation
- remote preview/unfurl verification

### Forbidden shortcuts

- do not do DiscordOS platform work here by default
- do not use ATLAS root as the product implementation surface

### First safe package

- explicit Fitness product/QA/LLEL package
or
- approved Fitness Supabase Mutation Pass 1 only

## Discord Work Lane

### Start conditions

- work belongs to Discord runtime, workflows, moderation, updates, feedback, or Music Sesh
- Discord-owned scope is explicit
- Fitness seam usage stays contract-based

### Required first checks

1. confirm owner surface is the Discord lane
2. confirm whether the task is docs-only, bootstrap, schema, or runtime work
3. confirm exact approval posture
4. confirm the latest DiscordOS planning receipt chain

### Required receipts

- DiscordOS inventory, contract, env/runtime, schema, cutover, and bootstrap receipts as applicable

### Approval-gated blockers

- DiscordOS bootstrap
- later schema/runtime cutover gates

### Forbidden shortcuts

- no hidden Fitness coupling by convenience
- no runtime cutover by implication from planning

### First safe package

- approved DiscordOS repo bootstrap only

Current reopen note:

- bootstrap is already complete
- the next Discord lane package should still be tiny: scaffold, runtime-shadow planning, or another explicit adapter/contract surface
- do not jump from scaffold state to runtime migration by momentum

## ATLAS Systems Lane

### Start conditions

- work belongs to governance, receipts, validation, `_stack`, Playbook-facing planning, book work, or stack topology
- work belongs at ATLAS root instead of an owner repo

### Required first checks

1. confirm owner surface is ATLAS systems
2. confirm the work is not actually repo-local implementation
3. confirm whether markers or gate posture will change
4. confirm the latest book/receipt state

### Required receipts

- ATLAS receipt or book update for durable state changes
- validation receipt after substantial work

### Approval-gated blockers

- none for docs-only continuation
- may not bypass another lane’s gate

### Forbidden shortcuts

- do not mutate owner-repo runtime by convenience from root
- do not treat planning as approval

### First safe package

- governance continuation
or
- `_stack` / Lifeline / doctrine design work

Current reopen note:

- the controlling ATLAS systems lane is now closeout and reconciliation
- continue with narrow non-gated retained-surface cleanup packages before reopening broad mutation lanes

## Shared Handoff Rules

- repo-local proof stays repo-local first
- `_stack` owns governed deploy execution
- Discord publication stays downstream of proof
- Fitness auth/profile truth stays Fitness-owned
- Discord-owned runtime state only moves through explicit contracts
- ATLAS records cross-repo consequence

## Marker Rules

- move markers only when durable ambiguity is reduced
- keep approval-gated lanes flat unless readiness or gate posture changed
- update the book-local marker table when the checkpoint changes marker truth
- do not treat receipt-only or review-only progress as `100%` if retained surfaces still exist

## Quick Reopen Checklist

Before reopening any lane:

1. read [Current State](01-current-state.md)
2. read [Approval Gates](04-approval-gates.md)
3. read [Current System Map / Graph](11-system-map-graph.md)
4. read [Restart And Handoff Guide](12-restart-and-handoff-guide.md)
5. confirm the lane’s first safe package

## Success Condition

The split is operational when:

- the next lane can be chosen without chat reconstruction
- owner boundaries are obvious
- first safe packages are bounded
- approval-gated blockers are explicit
- cross-lane shortcuts are treated as regressions

## Non-Goals

- no repo creation
- no code movement
- no data mutation
- no Vercel mutation
- no Discord runtime change
