## Product direction

**RECONCILED TARGET** - Atlas is a human-directed creation operating system
that turns intent into governed, verifiable software and artifacts while
preserving durable context, explicit ownership, and final human authority.

The first wedge is a voice-capable software, app, and tool builder with:

- repository ingestion and compatibility analysis;
- bounded governed execution;
- deterministic tests, diffs, and previews;
- durable context and artifact provenance;
- reversible side effects and human approval.

The wedge does not authorize a monolithic AGI, automatic production mutation,
a new general-purpose Atlas server, a selected memory backend, XR/device
deployment, or simultaneous construction of every surface.

## System composition

The Creation OS composes the existing owner model:

- Atlas root: kernel governance, topology, contracts, approvals, markers,
  accepted receipts, and cross-repo projection;
- Playbook: doctrine, profiles, reusable rules, and repo verification;
- Atlas Contracts: versioned interoperability and identity;
- Cortex: advisory intelligence, context, routing, synthesis, and read models;
- `_stack`: governed execution and delivery actions;
- DiscordOS: one logical board, publication, and readback writer;
- owner repositories: product, code, runtime, release, and domain truth.

Full host capability remains distinct from external, production, publication,
purchasing, and device-actuation authority.

## Two loops

### Deterministic builder loop

```text
goal -> spec -> repo ingestion -> compatibility plan -> bounded change
-> tests and preview -> evidence and receipt -> human acceptance
-> separately authorized side effect
```

### Conversational creative loop

```text
voice or text exploration -> context and options -> branch or preview
-> user refinement -> selected candidate -> deterministic builder admission
```

Conversational speed and creativity never bypass deterministic execution,
policy, tests, receipts, owner truth, or human approval.

## Bootstrap and memory

The proposed bootstrap artifact is a signed, versioned, minimal recovery
pointer into governed truth. It points to source hierarchy, policy, owner and
contract registries, retained state catalogs, receipt indexes, and recovery
checkpoints. It does not contain all memory, secrets, private keys, copied
owner truth, or execution authority.

The decision remains proposed in the
[bootstrap manifest ADR](../atlas/decisions/adr-signed-versioned-atlas-bootstrap-manifest.md).
Signing, key custody, schema format, storage, replication, and recovery UX are
unresolved.

Memory remains tiered:

1. versioned source and owner authority;
2. accepted operational evidence and receipts;
3. durable imports and artifacts;
4. rebuildable indexes and Cortex read models;
5. bounded working context;
6. disposable state.

Compaction must preserve sources, digests, scope, decisions, unresolved risks,
authority qualifiers, supersession, and replay paths. No database, vector
store, graph store, cache, or object store is selected by this chapter.

## Repository ingestion candidate

The reconciled pipeline is:

```text
manifests, lockfiles, changelogs, and OpenAPI
-> syntax and deterministic indexing
-> LSP and selected static analysis
-> compatibility graph
-> migration plan, CI matrix, adapters, and evidence
```

Specific parsers, analyzers, graph engines, and storage products remain
research or ADR choices.

## Roadmap and gates

Creation OS development follows the current Atlas pre-development gate and is
split into independently measurable stages:

1. software builder;
2. voice and creative loop;
3. spatial blueprint surface;
4. device gateway and safe actuation;
5. scale, team, enterprise, and provider expansion.

The authoritative candidate registry is
[Atlas Full-System Re-evaluation Lanes](../registry/ATLAS-FULL-SYSTEM-REEVALUATION-LANES.json).
Every Creation OS candidate remains percentage-null with an unknown numerator
and denominator until an authorized marker audit accepts measurement.

## Relationship to the existing endgame

This chapter extends the later program in
[Vision And Endgames](13-vision-and-endgames.md#post-preparation-development-endgame)
and [Operating Model](03-operating-model.md#post-preparation-development-program).
It does not replace or reopen historical Clean and Re-sync markers.

The later post-preparation ecosystem program explicitly retains:

- finishing Lifeline, Foundation, Cortex, `_stack`, DiscordOS, Playbook, Atlas
  root and wiring, Atlas Contracts, Atlas Control, and the Atlas Book;
- deterministic integration through contracts, execution, evidence, receipts,
  GitHub, boards, publications, knowledge promotion, and recovery;
- evidence-backed ChatGPT/Codex-to-Cortex conversion to the highest safely
  justified degree;
- evidence-backed Vercel/Supabase-to-Lifeline/Foundation conversion to the
  highest safely justified degree;
- current external platforms as governed adapters until parity, quality,
  security, reliability, observability, cost, migration, rollback, and
  post-cutover health are proved.

Fitness, Mazer, and Socials OS remain separate owner lanes. Atlas may promote
reusable contracts, patterns, infrastructure, and evidence without absorbing
their product implementation.

## Whole-stack text convergence

Before final canonicalization, the Atlas Book must ultimately inventory,
adopt, link, and reconcile applicable text across every governed Atlas
repository. Early Playbook research, planning, doctrine, prompts, and notes
require a dedicated archaeology pass because they predate much of the stack.

That future convergence must preserve owner authority, source references,
digests, privacy, freshness, supersession, and exclusions. It must not bulk
copy, delete, consolidate, or transfer Atlas Book or Playbook authority without
an accepted ADR, reversible migration plan, source-preservation proof, and
operator acceptance.

## Unresolved operator decisions

No success or kill threshold is ratified yet. The following measurement
families remain explicit placeholders:

- accepted end-to-end project outcomes;
- builder reliability by supported repository class;
- escaped defects and rollback events;
- authority violations and recovery success;
- voice latency and creative-to-builder conversion;
- repeated use and retention;
- paid outcomes, conversion, cost, and margin;
- measured spatial value;
- device safety and actuation evidence.

Product, monetization, threshold, and kill decisions belong to the unmeasured
`lane-pmf-monetization-success-kill-criteria` candidate and require operator
ratification.
