## 9. Reusable discoveries for Playbook

### Rules

- **Rule — Owner truth wins:** ATLAS coordinates and projects; owner repositories own implementation and product truth.
- **Rule — Historical completion does not prove current health:** closed markers are provenance; current evidence and current denominators govern present claims.
- **Rule — Classify before cleanup:** clean does not mean removal-safe, and generated residue does not automatically mean source dirt.
- **Rule — One logical writer per mutable plane:** especially DiscordOS board/publication mutation and canonical `_stack` root generation.
- **Rule — Security gates are non-substitutable:** CI success, deployment readiness, or marker progress cannot clear a critical secret-containment gate.
- **Rule — Products validate platform work:** solve the real Fitness/Mazer/Discord problem first, then promote a reusable pattern after repeatable proof.
- **Rule — Real data before learning:** no retrieval, personalization, or model claims over synthetic/unverified data.
- **Rule — No silent data loss:** migrate, warn, partially import with disclosure, or block.
- **Rule — Proof before completion:** actual diffs, tests, receipts, deployment correlation, and readback outrank summaries.

### Patterns

- **Pattern — Historical harvest → source classification → owner verification → governed promotion.**
- **Pattern — Card/initiative → reviewed packet → bounded worker → diff → proof → acceptance receipt → projection.**
- **Pattern — Owner cleanup → clear verifier residue → regenerate root lock/inventory → publish read-model truth.**
- **Pattern — Proposal → schema/fixture proof → one producer → one consumer → adoption claim.**
- **Pattern — Read-only external evidence before mutation authority.**
- **Pattern — Separate audit denominators from child-lane denominators.**

### Failure modes

- **Failure Mode — 100%-as-health inference:** a dated marker is treated as proof of current system health.
- **Failure Mode — Transcript archaeology as authority:** a chat plan overrides current owner truth.
- **Failure Mode — Cleanup by inference:** branches, worktrees, archives, or repos are deleted because they look old or clean.
- **Failure Mode — READY-as-release inference:** Vercel READY or Supabase ACTIVE_HEALTHY is treated as source/release/health proof.
- **Failure Mode — Cross-plane ownership collapse:** ATLAS, `_stack`, DiscordOS, Cortex, Lifeline, or Foundation silently absorbs another owner’s mutation authority.
- **Failure Mode — Synthetic capability illusion:** generated or template data is presented as learning/retrieval capability.
- **Failure Mode — Board projection drift:** checked-in card counts, stale documents, and live Discord state are merged without freshness and readback boundaries.

## 10. Reusable rules, patterns, and failure modes

### Rules

- **Rule — Product-driven platform evolution:** A platform capability must solve a proven Fitness, Mazer, Discord, or operator problem.
- **Rule — Owner-repo truth:** ATLAS coordinates and retrieves; owner repos own implementation truth.
- **Rule — Proof before completion:** Tests, diffs, deployments, receipts, and live checks outrank summaries.
- **Rule — Real data before learning:** No retrieval, personalization, or model claims over synthetic/unverified data.
- **Rule — Docs unlock code:** Documentation clarifies boundaries and gates; it does not replace implementation.
- **Rule — Discord is not the control plane:** Discord is a community/product surface, not durable system authority.
- **Rule — No silent data loss:** Migrate, warn, partially import with disclosure, or block.
- **Rule — Preserve canonical source:** Deploy from canonical Git-backed source, not dirty or ambiguous workspaces.
- **Rule — Bound autonomy:** Parallel workers need disjoint ownership, explicit contracts, verification, and rollback.

### Patterns

- **Pattern — Experiment → Adopted → Verified → Governed**
- **Pattern — Card → Reviewed Packet → Diff → Proof → Completion Review → Update → Doctrine**
- **Pattern — Manifest → Playbook Defaults → Lifeline Execution → Receipt → ATLAS Checkpoint**
- **Pattern — Complete Vertical = Core + Evaluation + Interface + Documentation**
- **Pattern — Products as testbeds:** Fitness and Mazer generate real pressure that validates the platform.
- **Pattern — Restart hierarchy:** Book summary → owner-repo docs → receipts/markers → implementation.

### Failure modes

- **Failure Mode — Platform-before-product:** Infrastructure expands without measurable product pressure.
- **Failure Mode — Summary-truth drift:** The assistant claims completion that the diff does not prove.
- **Failure Mode — Transcript archaeology:** Critical state exists only in old chats.
- **Failure Mode — Synthetic capability illusion:** Generated data makes an unfinished system look intelligent.
- **Failure Mode — Ownership collapse:** ATLAS, Lifeline, `_stack`, Cortex, or Discord absorbs another system’s role.
- **Failure Mode — Dirty-source deployment:** Production cannot be traced to canonical Git truth.
- **Failure Mode — Board duplication:** Recovered plans become new duplicate cards instead of reconciling existing work.
- **Failure Mode — Milestone flattening:** Forty cards are treated as equal instead of serving the next playable/releasable gate.
- **Failure Mode — Advanced-AI distraction:** Personalization/research delays a fun, stable, instrumented product.
